# Procedural Gateway — how work is executed in this repository

> Binding on every session. Established 2026-07-28 at Harvey's direction; companion to
> `GATEWAY_BEHAVIOURAL.md` (register and conduct). This document is the cursor rules
> **calibrated to the SDT engine** — the generic application-development set translated to a
> physics research codebase — plus the procedures this project has learned the hard way.

## §1. The order of truth

1. `Engine/include/sdt/laws.hpp` is the single source of every constant and derived
   expression. **No file redefines a constant the engine exposes; no local constant
   namespaces.** (This is the engine's form of "single source of truth / DRY.")
2. `sdt::laws::measured` is the only surface where the world enters: the four irreducibles'
   readings and measured observables in measured units. Nothing fitted enters there.
3. `Theory/00_Ruleset.md` governs physics content; canon under `Engine/include/sdt/` and
   `Laws/` is **propose-and-wait** — no edit, including comments, without explicit approval.
4. Direct-execution assessments (`*_ASSESSMENT.md`; historical `*_VERDICT_DIRECT_*.md`) are
   the only citable investigation conclusions. Regenerated reports are regenerated by their
   tool — never hand-edited.

## §2. Change protocol (calibrated: careful_changes · dont_rewrite_files · no_new_patterns)

- Make only the requested change, or a change fully understood end to end — including its
  downstream consumers (grep before renaming; check who includes, who links, who translates).
- Edit in place; do not rewrite a file wholesale when a diff serves. Wholesale replacement is
  reserved for files whose purpose has been replaced, and says so in the commit.
- Follow the established pattern of the surrounding code or documents; introduce a new
  pattern only when the existing one cannot carry the requirement, and retire the old one in
  the same change rather than leaving two.
- Public-site changes propagate: `Release/HTML_SDT_Website/` edits mirror to `docs/` in the
  same working session; changed English strings on i18n-wired pages are re-keyed and
  retranslated in the same change.
- **Deletion policy (absolute).** No scripted or bulk deletion of files, ever — no `rm` in
  loops, no `git rm -r`, no deletion buried inside a compound command. A file is deleted only
  after it has been read, its role stated, and the deletion approved explicitly, item by
  item. Prefer moving to an appropriate folder over deleting. (Origin: a session on
  auto-approve deleted the entire Benchmarks suite. Never again.)

## §3. Investigation procedure (this project's own, now standard)

1. **Pre-registration before instrumentation.** Thresholds, tolerances, conventions, and
   rejection criteria are written into the PROMPT and RUN_LOG before the tool exists. A
   rejection criterion is only registered if its rejection class is populated — a criterion
   that cannot be met by any physically possible outcome is not a test.
2. **Instrument validation before use.** Every numerical instrument is validated on problems
   with known answers before it touches the object under study. An instrument fault found on
   the object is a validation failure, not a result.
3. **Single-pass comparison.** Where a claim concerns a curve, a family, or a chart, the
   whole range is computed in one pass from the pre-registered rule and compared once. No
   mid-range adjustment; a rule that needs retuning partway is itself the finding.
4. **Two-route verification.** Load-bearing numbers are reached by two independent routes
   (analytic vs numerical, direct vs fitted) and the routes must agree within stated
   tolerance before the number is quoted.
5. **Direct execution.** All investigation, audit, and assessment work runs in the main
   session. Delegated-agent output is not citable.
6. **Label discipline.** Every reported number carries exactly one tag — MEASURED-INPUT ·
   DERIVED · COMPUTED · CALIBRATED(n) · OBSERVED · PENDING — under the behavioural §1
   vocabulary. A measured difference the model *names* is MEASURED, however good the story.
7. **Review checklist (from the 2026-07-26 refereeing audit):** no framework judged by its
   competitor's fitting machinery · no theory-derived decomposition used as data · a
   framework's own derived laws are legal inputs to its own chains · first-pass models gated
   against same-fidelity comparators · both parameter ledgers on the table in any comparison
   · alignment with measurement never counts against a result — origin decides.

## §4. Code standards (calibrated: keep_code_simple · clean_organized · line limits · no_mock_data · no_scripts_in_files · dev_test_prod)

- C++20, header-only engine style: `inline constexpr` for constants, `[[nodiscard]] inline
  auto` for derived functions, `std::numbers::pi`, cite the theorem (T1–T18) in a comment.
- Standalone tools follow the standard compile line (`g++ -std=c++20 -IEngine/include …`),
  stay small, print their own results with labels, and read every constant from the engine.
- Scratch work, binaries, and one-off scripts live in the session scratchpad — never
  committed. The repository holds sources, data with provenance, and records.
- Synthetic or toy inputs are labelled demo/toy in the output itself and are never blended
  with measured anchors in a comparison. (The engine's form of "no mock data.")
- Datasets enter through `Datasets/` with a manifest row (sha256, provenance, date); files
  over 100 MB live outside the repository with a manifest pointer.
- Dropped as inapplicable to this codebase: GUI component/button handling, `.env` handling
  (no environment secrets exist here). Their spirit — don't touch configuration you don't
  own — survives as the canon propose-and-wait rule.

## §5. Records and registers (calibrated: maintain_project_goals · maintain_todo)

- Every investigation folder carries its PROMPT (pre-registration), its tool, its output
  capture, and its assessment. Sequence numbering continues per category; category READMEs
  updated when an investigation is added.
- Retractions and corrections are recorded in place, dated, with the reason — never silent
  deletion. Withdrawn claims remain visible as withdrawn.
- On any exclusion or open result, trace the fault to its premise before closing: what
  assumption produced it, what would repay it, and where that is recorded.
- The open-problems ledger (`Theory/03_Open_Problems.md`, the causal chain's L20) is the
  project TODO; items enter and leave it by dated entry.

## §6. Precedence

This gateway governs procedure. `GATEWAY_BEHAVIOURAL.md` governs register and conduct.
`Theory/00_Ruleset.md` and the engine's prohibitions govern physics content and outrank both
wherever they touch.
